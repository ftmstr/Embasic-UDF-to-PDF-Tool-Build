## Reproduced P0 resource amplification
The full merge admits up to 160 UDFs. Each compressed PNG payload may be <=1 MiB and its IHDR may independently allow up to 4,000,000 decoded pixels. `PdfExporter.Layout.image` calls `DocumentElements.decodeBoundedPng`, then `LosslessFactory.createFromImage`, retaining image XObjects in a single PDDocument. The 2,048 PDF page cap does not constrain decoded image rasters. One 4MP 32-bit RGBA per 160 docs mathematically represents 640 million pixels (at least 2.56 GB in source rasters), much greater than the 512MiB Java heap used in Windows CI. The issue is a reproducible uncontrolled aggregate memory-exposure path; an actual 2.56GB OOM crash was not deliberately executed.

## Narrow fail-closed correction
Add `MAX_MERGED_IMAGE_PIXELS=16_000_000L` to `PdfExporter.java`. After existing source/text and page-geometry gates, but BEFORE PDDocument allocation, sum each ImageBlock's PNG IHDR width×height with long arithmetic, reject malformed/absent IHDR, invalid dimensions or aggregate limit overflow. Count pixels across the entire ordered merge, not once per document/page; preserve the per-image <=4MP and <=1MiB compressed checks and existing PNG CRC/zlib/palette decoder. The cap bounds nominal raw 4-channel raster exposure to 64 MB before PDFBox overhead; it is not a guarantee against every possible memory attack. A 4MP image remains permissible if the whole merge stays within cap. Preview deliberately skips whole-document aggregation to preserve first-page-only lazy behavior.

Single rights-clean regression in `PdfImagePixelFidelityTest.java`: construct a tiny compressed grayscale PNG with 4000×1000 IHDR and correct PNG signature, CRC and zlib. Four references exactly use 16MP and pass the SAME preflight; five exceed and are rejected, including after a document boundary. A real `PdfExporter.save` with five images refuses approved-target overwrite, preserves original bytes and cleans staging, without decoding huge rasters.
