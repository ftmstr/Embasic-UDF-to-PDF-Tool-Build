## New source-proven P0 resource bug
The UDF reader limits distinct ZIP PNGs to 64 and 8 MiB total encoded payload, but XML image **uses** were unbounded except broad 4 MiB XML and 65,536-node SAX gates. `UdfReader.parse` iterated each `<image ref='media/one.png'.../>`, called `DocumentElements.image` to decode the same valid PNG anew, and created a new `ImageBlock` cloning the PNG byte array for every use. Thousands of uses of ONE file could thus exhaust heap or stall parsing before `PdfExporter.renderInternal`'s TUR425 total pixel cap executes. This is a deterministic unbounded-input-amplification path; actual heap-exhaustion tests were deliberately not run. A successful UDF/PDF result may not silently omit images.

## Minimal solution
`app/src/main/java/com/embasic/publicapp/UdfReader.java`: per-document `MAX_IMAGE_BLOCKS=64`, `MAX_RENDERED_IMAGE_BYTES=8*1024*1024`, counting uses and retained encoded byte instances across all images. Before any new ZIP-referenced image's ImageIO decode, check both use count and aggregate encoded bytes of the referenced payload. Count inline base64 images too, after their existing per-image bounded decode. Fail closed on an over-limit source, leaving no partial output. Keep 64 small repeated images admissible, preserve strict image validation, unique-media ZIP budget, selected order and full-export pixel budget; no code from private or native UYAP.

`app/src/test/java/com/embasic/publicapp/UdfRepeatedImageBudgetTest.java`: two rights-clean JUnit methods, generated XML/ZIP and original PNG sources. (1) 64 valid repeated uses pass, 65 and 2048 image nodes fail early; one archive stays small. (2) a deterministic noisy 512×512 RGB PNG of approx 0.75 MiB fits the 1 MiB distinct-image limit; aggregate repetitions fitting 8 MiB pass, the first exceeding use fails. No large OOM stress, no authentic native UYAP golden. Source blob `5466a1c53a754fa272bb1d187f414608ab17e389`; test blob `4dd9e00fa3982a95a37423960b0b02c7cc2cc3e4`.
