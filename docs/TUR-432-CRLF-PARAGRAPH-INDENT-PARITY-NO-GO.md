## Novel text-layout P0 source evidence
At the baseline, UdfReader handles every paragraph's first XML content range by examining the skipped source substring. It reattaches the skipped spaces *only if the ENTIRE substring contains ASCII spaces*. Thus a document's UDF raw UTF-16 `X\\n    Y` with two successive XML paragraphs and second startOffset=6 silently becomes parsed second Run `Y` instead of `    Y`: four visible indentation spaces after a structural newline disappear. The PDF renderer's paragraph layout uses those spaces for horizontal placement, so silently losing them changes PDF glyph x-coordinates. TUR396 previously fixed pure all-space gaps, not newline+space or CRLF+space mixed gaps.

## Minimal fix
`app/src/main/java/com/embasic/publicapp/UdfReader.java`: keep the existing identical interior-run gap behavior. At the *first run* of a paragraph, retain only ASCII spaces after the last structural LF, CR or TAB in the skipped UTF-16 substring; retain pure all-space gap unchanged. Structural breaks and spaces before the last break remain structural, not new PDF paragraphs. This is not a Unicode shaping change. Source Git blob `39ddccc7c09f1533d82e5389985e99a20e332f36`.
`app/src/test/java/com/embasic/publicapp/UdfStructuralLineIndentTest.java`: original rights-clean synthetic XML, two tests: (1) second paragraph `X\\n    Y` must retain four spaces, and actual PDFBox glyph-position X(Y) > X(X)+5pt; (2) XML-escaped CRLF + spaces, LF+TAB + spaces, CRLF alone and trailing spaces *before* LF are separately checked.
